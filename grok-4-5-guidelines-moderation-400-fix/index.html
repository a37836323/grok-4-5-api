grok-4.5 用 guidelines 参数收紧内容审核：写法、报错与验证

如果你的产品面向普通用户，希望 grok-4.5 的回答避开性暗示、血腥暴力描写或脏话，可以在请求里加 xAI 10 月新增的 guidelines 数组，把对应类别设为 decline。加了之后如果请求直接返回 400 或 422，通常是数组格式写错，或者请求里同时带了 stop、n 大于 1 这类不能和 guidelines 一起用的设置。本页根据 xAI 官方的 Custom Moderation Controls 文档、发布说明和 Chat Completions 接口参考整理写法、报错对照和验证方法。

guidelines 参数是什么，grok-4.5 能用吗？

xAI 发布说明在 10 月一栏写明：现在可以给文本 API 请求设置内容准则，在 Chat Completions 或 Responses API 请求里加一个 guidelines 数组，控制 Grok 怎么处理 nsfw、violence、profanity 三类内容，Grok 会在生成回答时遵守这些准则。详细说明在 Custom Moderation Controls 文档：https://docs.x.ai/developers/advanced-api-usage/custom-moderation-controls 。

官方文档的示例用的是 grok-4.7，没有逐个列出支持的模型；文档只写明两类请求不能用 guidelines：多智能体模型（例如 grok-4.20-multi-agent）和 deferred completions（延迟补全）。grok-4.5 的官方模型页 https://docs.x.ai/developers/models/grok-4.5 标注它是推理模型，不是多智能体模型，不在这份例外名单里。是否真正生效，按本页最后的验证方法用自己的请求确认。

这个参数目前只能让审核更严格，不能放宽。文档的说法是：对你列出的类别选择进一步加强的行为，目前唯一可选的行为是 decline；没有列出的类别继续使用模型默认的审核行为。所以只需要列出你想改变的类别。

三个类别设成 decline 后，模型会怎么回答？

nsfw 设为 decline：避免性暗示和性化的对话，但仍会回答关于性话题的教育类和医疗临床类问题。

violence 设为 decline：避免血腥暴力的描写，仍然可以谈历史和新闻，只是不写血腥细节。

profanity 设为 decline：回答里不使用脏话；如果请求本身只是要脏话，或者请求内容极具冒犯性，会拒绝。

官方特别说明两点：一是 Grok 用自己的话遵守准则，返回的响应结构和不带 guidelines 时完全一样，不会多出一个“已拦截”之类的字段；二是上面只是概括描述，xAI 之后可能调整细节。也就是说，不能指望在响应里读到审核结果，需要自己按内容判断。

请求里 guidelines 应该怎么写？

数组里每一项有三个字段：type 固定写 policy，category 填 nsfw、violence 或 profanity，behavior 填 decline。例如同时限制暴力和色情，就写两项：{"type": "policy", "category": "violence", "behavior": "decline"} 和 {"type": "policy", "category": "nsfw", "behavior": "decline"}。同一个类别只能出现一次。

用 Chat Completions 接口（/v1/chat/completions）时，把 guidelines 作为请求体的顶层字段，和 model、messages 同一层，不要放进某条消息里。用 Responses 接口（/v1/responses）时，同样放在请求体顶层，和 model、input 同一层。

用 OpenAI 官方 SDK 时要注意：OpenAI SDK 里没有定义 guidelines 这个参数。Python SDK 要放进 extra_body，例如 client.responses.create(model=..., input=..., extra_body={"guidelines": [...]})；JavaScript SDK 直接和其他参数一起传即可。用 xAI 自己的 Python SDK 时，在 client.chat.create 里传 guidelines=[...]，它会把准则保存在这个 chat 上，之后每次 sample 都会带上。

guidelines 只对带着它的那一次请求生效。多轮对话想全程生效，每次请求都要带上；用 OpenAI SDK 或直接发 HTTP 的代码，最好在统一封装请求的地方加，避免某些入口漏带。

加了 guidelines 后报 400 或 422，按这张对照查

官方文档说明：API 会在运行模型之前检查 guidelines，无法应用时直接返回错误，模型不会运行。各状态码的原因如下。

422：category 或 behavior 不是已知取值，例如拼错成 nsfw_content、把 behavior 写成 block。官方说错误信息里会列出合法取值，照着改即可。

400：同一个 category 在数组里出现了不止一次。合并成一项。

400：type 不是 policy。每一项都要写 "type": "policy"，不能省略或写成别的值。

400：这个请求不能使用 guidelines。包括用了多智能体模型、走 deferred completions，以及请求里没有服务端工具、也没有文件附件，却设置了 stop 或者 n 大于 1。官方说这种情况下错误信息会写出是哪个模型或哪个选项导致的。

对 grok-4.5 来说，stop 本来就有问题：xAI 推理指南写明 presencePenalty、frequencyPenalty 和 stop 不能用于推理模型，带上会返回错误（https://docs.x.ai/developers/model-capabilities/text/reasoning ）。所以接入 guidelines 前，先把请求里的 stop 去掉；n 保持默认或写 1。

如果用 xAI Python SDK，类别或行为写错时，SDK 在发请求前就会抛出 ValueError；其他错误由 API 以 gRPC 的 INVALID_ARGUMENT 状态返回。

按什么顺序排查，怎么确认已经生效？

第一步，保存一次失败请求的完整请求体和响应体，看状态码是 400 还是 422，再看错误信息里点名的是字段取值、模型还是某个选项。

第二步，对照上一节逐项检查：每项三个字段是否齐全、type 是否为 policy、类别是否重复、取值是否拼写正确；请求里有没有 stop、n 大于 1；模型名是不是 grok-4.5（官方模型页列出的别名还有 grok-4.5-latest 和 grok-build-latest），有没有误用多智能体模型或 deferred completions。

第三步，确认 guidelines 放在请求体顶层。用 OpenAI Python SDK 时检查是否按官方写法放进了 extra_body，而不是直接作为 create() 的参数传入。

第四步，验证效果。因为官方说响应结构不变，没有专门的审核字段，验证只能看内容：用同一个容易触发该类内容的测试提示，分别发一次不带 guidelines 和带 guidelines 的请求，对比回答是否回避了对应内容。模型输出本身有随机性，建议多发几次再下结论，并保留测试提示和结果作为上线记录。

成功标准：带 guidelines 的请求返回 200、不再出现 400/422；回答在你限制的类别上明显收敛，其他类别和正常问题的回答不受影响。

通过中转站调用 grok-4.5 时，guidelines 会生效吗？

guidelines 是 xAI 官方接口的参数。通过中转站调用时，这个字段会不会原样转发到 xAI，取决于平台的转发方式；本页没有用真实请求实测，无法保证和官方直连效果一致。

OpenLux 价格接口显示 grok-4.5 支持的接口类型是 openai（OpenAI 兼容）和 anthropic，不含 OpenAI Responses。用 OpenAI 兼容方式时，Base URL 填 https://api.openlux.ai/v1，请求 /v1/chat/completions，把 guidelines 写在请求体顶层；xAI 官方文档只说明 Chat Completions 和 Responses 接受 guidelines，没有提到 Anthropic 格式的请求，用 Anthropic 协议调用时不要依赖这个参数。

稳妥的做法是：按上一节的方法分别对比带与不带 guidelines 的输出，确认中转后确实有效再上线；同时在自己的应用里保留必要的内容过滤，不要只靠这一个参数。如果按本页改完仍然报错，把完整响应体和请求时间交给平台核对。费用以官网价格页和平台显示为准。
