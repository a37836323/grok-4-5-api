grok-4.5 请求报错：先删掉 stop、presencePenalty 和 frequencyPenalty

从旧模型或其他厂商的代码切换到 grok-4.5 后，如果请求一发出就返回错误，先检查参数里有没有 stop、presencePenalty 或 frequencyPenalty。xAI 官方推理指南写明：这三个参数不能用于推理模型，带上它们的请求会返回错误；grok-4.5 是推理模型，推理不能关闭。本页根据 xAI 官方推理指南、grok-4.5 模型页和 Responses 接口文档，说明怎么改参数、reasoning_effort 能填什么，以及改完怎么验证。

为什么 grok-4.5 的请求带 stop 或 presencePenalty 会报错？

xAI 官方推理指南列出 grok-4.7、grok-4.6 和 grok-4.5 都支持 reasoning_effort 参数，并在同一段说明：presencePenalty、frequencyPenalty 和 stop 不能用于推理模型，包含这些参数的请求会返回错误。指南没有给出具体的状态码和报错原文，所以排查时以响应体里的错误信息为准。

grok-4.5 的官方模型页把 Reasoning 一项标为 Yes，而且推理指南说明推理不能关闭。也就是说，不存在「关掉推理就能继续用 stop」的办法，只能把这几个参数从请求里去掉。

官方推理指南里的参数名是驼峰写法。如果你的代码、框架或客户端配置里用的是 presence_penalty、frequency_penalty、stop 这类下划线写法，也要一起检查。Responses 接口文档在响应字段里把 presence_penalty 和 frequency_penalty 标注为 Responses API 不支持。

官方资料：推理指南 https://docs.x.ai/developers/model-capabilities/text/reasoning ，grok-4.5 模型页 https://docs.x.ai/developers/models/grok-4.5 。

grok-4.5 的 reasoning_effort 能填哪些值？

推理指南的说明：不写 reasoning_effort 时默认是 high，推理不能关闭。grok-4.5 在指南的对照表里可选 low、medium、high 三档，默认 high；effort 控制的是推理深度，档位越高，用掉的推理 token 越多。

关于 xhigh，官方两处说法不一致：推理指南写明 xhigh 只在 grok-4.6 及之后可用，对 grok-4.5 这类不支持的模型，传 xhigh 会按 high 处理；而 grok-4.5 的模型页把 low、medium、high、xhigh 都列为支持的取值。在官方统一说法之前，grok-4.5 想要可预期的结果，建议直接写 high，不要依赖 xhigh。

xAI 在 7 月的发布说明中介绍 grok-4.5 时，也写的是推理强度可配置为 low、medium 或 high，默认 high。发布说明地址：https://docs.x.ai/developers/release-notes 。

请求里 effort 应该怎么写？

官方推理指南给了几种写法（示例里的模型是 grok-4.7，换成 grok-4.5 时 effort 取值按上一节）：用 OpenAI Python SDK 调 Responses 接口时，在 client.responses.create 里传 reasoning={"effort": "high"}；用 curl 请求 https://api.x.ai/v1/responses 时，在 JSON 请求体里放 "reasoning": {"effort": "high"}；用 xAI Python SDK 时，在 client.chat.create 里传 reasoning_effort="high"；用 Vercel AI SDK 时，写在 providerOptions 的 xai.reasoningEffort 里。

Responses 接口文档还说明，请求体里的 reasoning_effort 是 reasoning.effort 的非标准替代写法，取值相同，只有在 reasoning 字段没有设置时才会读取它。所以同一个请求里不要两处都写、而且写的值不同，否则以 reasoning.effort 为准，容易误以为 reasoning_effort 没生效。

接口文档对 reasoning.effort 的说明是：支持的取值和默认值取决于模型。换模型时，effort 取值要按新模型重新核对。

按什么顺序排查和修复？

第一步，保存一次失败请求的完整请求体和响应体，确认模型名是 grok-4.5（模型页列出的别名还有 grok-4.5-latest 和 grok-build-latest），并记下错误信息里提到的参数名。

第二步，在请求体里搜索 stop、presencePenalty、frequencyPenalty 以及对应的下划线写法，全部删除。代码里没写也报错时，检查所用 SDK、框架或客户端的配置项、默认参数模板里是否设置了这些参数。

第三步，检查 effort 写法：Responses 请求用 reasoning.effort，或者只用 reasoning_effort 一种写法；取值用 low、medium 或 high。

第四步，原来依赖 stop 在某个标记处截断输出的，官方推理指南没有给出替代参数。如果目的是让输出符合固定格式，可以考虑结构化输出，grok-4.5 模型页把 Structured outputs 标为支持；否则就在拿到完整输出后由自己的代码处理。

第五步，删完参数后先用一句短提示发最小请求，确认不再报错，再恢复原来的业务请求。

改完以后怎么确认请求正常、推理强度生效？

第一，最小请求返回成功，响应里有正常输出，不再出现参数相关的错误。

第二，看响应的 usage。推理指南说明用量指标里有 reasoning_tokens，推理 token 计入总消耗并计费。可以用同一个提示分别以 low 和 high 各请求一次，对比 reasoning_tokens，确认 effort 设置被读到了。

第三，如果要在后续请求中带上推理上下文，推理指南说明：在 Responses API 里传 include: ["reasoning.encrypted_content"] 会返回加密的推理内容，可以在下一轮请求里原样传回；Chat Completions 没有存放这段密文的字段。

第四，批量改造前，确认所有调用入口（包括重试逻辑、备用模型切换逻辑）都已去掉不支持的参数，避免只有部分请求报错、难以定位。

通过中转站调用 grok-4.5，还会遇到这个报错吗？

上面的参数限制来自 xAI 官方接口。通过中转站调用时，请求会不会原样转发到 xAI、这几个参数会被透传还是被过滤、reasoning_effort 会不会生效，取决于平台的转发方式，本页没有实测，无法保证跟官方直连一致。

稳妥的做法是在发往中转站的请求里同样不带 stop、presencePenalty 和 frequencyPenalty，effort 用 low、medium 或 high。如果按上面的方法改完仍然报错，把完整响应体和请求时间交给平台核对。推理 token 计入用量，费用以官网价格页和平台显示为准。
